# Design patterns

## Creational patterns
The **Abstract Factory Design Pattern** is a creational design pattern that provides an interface for creating families of related objects without specifying their concrete classes. Instead of creating objects directly using constructors, the client uses an abstract factory that defines methods for producing different types of related objects, while concrete factories implement these methods to create specific product families. For example, a GUI application could use a Windows factory to create Windows-style buttons and checkboxes, or a macOS factory to create macOS-style buttons and checkboxes. This ensures that all created objects are compatible with each other and makes it easier to switch between product families without changing the client code.

The **Builder Design Pattern** is a creational design pattern that allows complex objects to be constructed step by step, separating the construction process from the final object's representation. Instead of using a constructor with many parameters, a builder provides methods to configure different properties of an object and then creates the final object once all necessary steps are completed. For example, when building a computer, you can use a builder to choose the processor, RAM, storage, and graphics card before assembling the final computer. This makes object creation more readable, flexible, and manageable, especially when objects have many optional or configurable properties.

The Factory Method Design Pattern is a creational design pattern that defines an interface for creating objects but allows subclasses to decide which specific class to instantiate. Instead of creating objects directly using constructors, the client calls a factory method that handles the object creation, hiding the details of which concrete class is being used. For example, in a notification system, a notification factory could create either an email notification, SMS notification, or push notification depending on the implementation of the factory method. This makes the code more flexible, reduces dependency on concrete classes, and makes it easier to introduce new types of objects without modifying existing client code.

The Prototype Design Pattern is a creational design pattern that allows new objects to be created by copying or cloning existing objects instead of creating them from scratch. It defines a prototype object that can be duplicated whenever a new instance is needed, often using a clone method. For example, in a game, you could create an enemy character with specific properties, such as health, speed, and appearance, and then clone it to create multiple identical enemies without having to configure each one individually. This pattern is useful when object creation is expensive or complex, as it saves time, reduces repetitive code, and allows objects to be created dynamically based on existing instances.

The Singleton Design Pattern is a creational design pattern that ensures a class has only one instance throughout the application and provides a global point of access to that instance. Instead of allowing objects to be created freely using constructors, the class controls its own instantiation and returns the same instance whenever it is requested. For example, a logging system could use the Singleton pattern to ensure that the entire application uses one shared logger instead of creating multiple logger instances. This pattern is useful when exactly one shared instance is needed, such as for configuration managers, logging systems, or database connection managers, helping to maintain consistency and avoid unnecessary object creation.

## Structural patterns
The Adapter Design Pattern is a structural design pattern that allows two incompatible interfaces to work together by acting as a bridge between them. Instead of changing the existing classes or their interfaces, an adapter translates the requests from one interface into a format that another interface understands. For example, if an application expects data in a specific format but an external library provides it in a different format, you can create an adapter that converts the external library's data into the format your application expects. This pattern is useful when integrating existing code, third-party libraries, or legacy systems without modifying their original implementation, making the code more flexible and reusable.

The Bridge Design Pattern is a structural design pattern that separates an abstraction from its implementation so that both can evolve independently without being tightly coupled. Instead of combining different variations into a large hierarchy of subclasses, the pattern uses composition to connect an abstraction to an implementation through a shared interface. For example, in a remote control system, you could have different types of remote controls (basic or advanced) that work with different devices (TV or radio). By separating the remote controls from the devices, you can add new remote controls or devices independently without creating a separate class for every possible combination. This pattern is useful when you want to avoid complex class hierarchies and make a system easier to extend, maintain, and modify.

The Composite Design Pattern is a structural design pattern that allows individual objects and groups of objects to be treated in the same way by organizing them into a tree-like structure. It defines a common interface for both individual objects (leaves) and groups of objects (composites), allowing clients to interact with them without needing to know whether they are dealing with a single object or a collection. For example, in a file system, individual files and folders can both support operations such as displaying their names, while folders can contain multiple files and other folders. This pattern is useful when working with hierarchical structures, as it simplifies code, makes it easier to manage complex object hierarchies, and allows individual objects and groups to be handled consistently.

The Decorator Design Pattern is a structural design pattern that allows additional functionality to be added to an existing object dynamically without modifying its original class. Instead of creating multiple subclasses for every possible combination of features, the pattern uses decorator classes that wrap an existing object and extend its behavior while maintaining the same interface. For example, in a coffee ordering system, you could start with a basic coffee object and wrap it with decorators that add milk, sugar, or whipped cream, each adding extra functionality or cost. This pattern is useful when you want to extend an object's behavior flexibly at runtime, avoid creating too many subclasses, and follow the Open/Closed Principle by extending functionality without modifying existing code.

The Facade Design Pattern is a structural design pattern that provides a simplified interface to a complex system of classes, libraries, or subsystems. Instead of requiring the client to interact with multiple components and understand how they work together, the facade acts as a single entry point that handles the necessary interactions behind the scenes. For example, in a home entertainment system, a facade could provide a single watchMovie() method that automatically turns on the TV, configures the sound system, dims the lights, and starts the movie. This pattern is useful when you want to reduce complexity, hide implementation details, and make a system easier to use and maintain by providing a simpler interface to its underlying components.

The Flyweight Design Pattern is a structural design pattern that reduces memory usage by sharing common data between multiple objects instead of storing duplicate information in every instance. It separates an object's shared, reusable state (intrinsic state) from its unique state (extrinsic state), allowing multiple objects to reuse the same shared data while maintaining their individual properties. For example, in a game with thousands of trees, instead of creating a separate object containing the same texture, color, and model data for every tree, the game can share this information between all trees while storing each tree's unique position separately. This pattern is useful when an application needs to create or manage a large number of similar objects, as it reduces memory consumption and improves performance.

The Proxy Design Pattern is a structural design pattern that provides a substitute or placeholder object that controls access to another object. Instead of interacting directly with the original object, the client communicates with the proxy, which can perform additional tasks before or after forwarding requests to the real object. For example, in an application that displays large images, a proxy could delay loading an image until it is actually needed, saving memory and improving performance. Other common uses include controlling access to sensitive resources, caching results, and handling remote objects. This pattern is useful when you want to add an extra layer of control, security, or efficiency without modifying the original object's implementation.
