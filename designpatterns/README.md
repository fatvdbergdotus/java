# Design patterns
## Creational patterns

The **Abstract Factory Design Pattern** is a creational design pattern that provides an interface for creating families of related objects without specifying their concrete classes. Instead of creating objects directly using constructors, the client uses an abstract factory that defines methods for producing different types of related objects, while concrete factories implement these methods to create specific product families. For example, a GUI application could use a Windows factory to create Windows-style buttons and checkboxes, or a macOS factory to create macOS-style buttons and checkboxes. This ensures that all created objects are compatible with each other and makes it easier to switch between product families without changing the client code. [Example with a Mac or Windows GUI](https://refactoring.guru/design-patterns/abstract-factory/java/example)

The **Builder Design Pattern** is a creational design pattern that allows complex objects to be constructed step by step, separating the construction process from the final object's representation. Instead of using a constructor with many parameters, a builder provides methods to configure different properties of an object and then creates the final object once all necessary steps are completed. For example, when building a computer, you can use a builder to choose the processor, RAM, storage, and graphics card before assembling the final computer. This makes object creation more readable, flexible, and manageable, especially when objects have many optional or configurable properties. [Example with building a sports car step by step](https://refactoring.guru/design-patterns/builder/java/example)

The **Factory Method Design Pattern** is a creational design pattern that defines an interface for creating objects but allows subclasses to decide which specific class to instantiate. Instead of creating objects directly using constructors, the client calls a factory method that handles the object creation, hiding the details of which concrete class is being used. For example, in a notification system, a notification factory could create either an email notification, SMS notification, or push notification depending on the implementation of the factory method. This makes the code more flexible, reduces dependency on concrete classes, and makes it easier to introduce new types of objects without modifying existing client code. [Example with a Windows 10 GUI or HTML layout](https://refactoring.guru/design-patterns/factory-method/java/example)

The **Prototype Design Pattern** is a creational design pattern that allows new objects to be created by copying or cloning existing objects instead of creating them from scratch. It defines a prototype object that can be duplicated whenever a new instance is needed, often using a clone method. For example, in a game, you could create an enemy character with specific properties, such as health, speed, and appearance, and then clone it to create multiple identical enemies without having to configure each one individually. This pattern is useful when object creation is expensive or complex, as it saves time, reduces repetitive code, and allows objects to be created dynamically based on existing instances. [Example with cloning shapes](https://refactoring.guru/design-patterns/prototype/java/example)

The **Singleton Design Pattern** is a creational design pattern that ensures a class has only one instance throughout the application and provides a global point of access to that instance. Instead of allowing objects to be created freely using constructors, the class controls its own instantiation and returns the same instance whenever it is requested. For example, a logging system could use the Singleton pattern to ensure that the entire application uses one shared logger instead of creating multiple logger instances. This pattern is useful when exactly one shared instance is needed, such as for configuration managers, logging systems, or database connection managers, helping to maintain consistency and avoid unnecessary object creation. [Example with constructing two instances of an Object which turn out to be the same](https://refactoring.guru/design-patterns/singleton/java/example)

## Structural patterns

The **Adapter Design Pattern** is a structural design pattern that allows two incompatible interfaces to work together by acting as a bridge between them. Instead of changing the existing classes or their interfaces, an adapter translates the requests from one interface into a format that another interface understands. For example, if an application expects data in a specific format but an external library provides it in a different format, you can create an adapter that converts the external library's data into the format your application expects. This pattern is useful when integrating existing code, third-party libraries, or legacy systems without modifying their original implementation, making the code more flexible and reusable. [Example which makes legacy square pegs compatible with new round pegs](https://refactoring.guru/design-patterns/adapter/java/example)

The **Bridge Design Pattern** is a structural design pattern that separates an abstraction from its implementation so that both can evolve independently without being tightly coupled. Instead of combining different variations into a large hierarchy of subclasses, the pattern uses composition to connect an abstraction to an implementation through a shared interface. For example, in a remote control system, you could have different types of remote controls (basic or advanced) that work with different devices (TV or radio). By separating the remote controls from the devices, you can add new remote controls or devices independently without creating a separate class for every possible combination. This pattern is useful when you want to avoid complex class hierarchies and make a system easier to extend, maintain, and modify. [Example with two different remotes applied to a radio and TV](https://refactoring.guru/design-patterns/bridge/java/example)

The **Composite Design Pattern** is a structural design pattern that allows individual objects and groups of objects to be treated in the same way by organizing them into a tree-like structure. It defines a common interface for both individual objects (leaves) and groups of objects (composites), allowing clients to interact with them without needing to know whether they are dealing with a single object or a collection. For example, in a file system, individual files and folders can both support operations such as displaying their names, while folders can contain multiple files and other folders. This pattern is useful when working with hierarchical structures, as it simplifies code, makes it easier to manage complex object hierarchies, and allows individual objects and groups to be handled consistently. [Example with a composition of shapes that are drawn on a Canvas](https://refactoring.guru/design-patterns/composite/java/example)

The **Decorator Design Pattern** is a structural design pattern that allows additional functionality to be added to an existing object dynamically without modifying its original class. Instead of creating multiple subclasses for every possible combination of features, the pattern uses decorator classes that wrap an existing object and extend its behavior while maintaining the same interface. For example, in a coffee ordering system, you could start with a basic coffee object and wrap it with decorators that add milk, sugar, or whipped cream, each adding extra functionality or cost. This pattern is useful when you want to extend an object's behavior flexibly at runtime, avoid creating too many subclasses, and follow the Open/Closed Principle by extending functionality without modifying existing code. [Example with a data stream that can be compressed and encrypted](https://refactoring.guru/design-patterns/decorator/java/example)

The **Facade Design Pattern** is a structural design pattern that provides a simplified interface to a complex system of classes, libraries, or subsystems. Instead of requiring the client to interact with multiple components and understand how they work together, the facade acts as a single entry point that handles the necessary interactions behind the scenes. For example, in a home entertainment system, a facade could provide a single watchMovie() method that automatically turns on the TV, configures the sound system, dims the lights, and starts the movie. This pattern is useful when you want to reduce complexity, hide implementation details, and make a system easier to use and maintain by providing a simpler interface to its underlying components. [Example with a simple video conversion function that does much work under the hood](https://refactoring.guru/design-patterns/facade/java/example)

The **Flyweight Design Pattern** is a structural design pattern that reduces memory usage by sharing common data between multiple objects instead of storing duplicate information in every instance. It separates an object's shared, reusable state (intrinsic state) from its unique state (extrinsic state), allowing multiple objects to reuse the same shared data while maintaining their individual properties. For example, in a game with thousands of trees, instead of creating a separate object containing the same texture, color, and model data for every tree, the game can share this information between all trees while storing each tree's unique position separately. This pattern is useful when an application needs to create or manage a large number of similar objects, as it reduces memory consumption and improves performance. [Example in which trees are planted efficiently by hashing their kind name](https://refactoring.guru/design-patterns/flyweight/java/example)

The **Proxy Design Pattern** is a structural design pattern that provides a substitute or placeholder object that controls access to another object. Instead of interacting directly with the original object, the client communicates with the proxy, which can perform additional tasks before or after forwarding requests to the real object. For example, in an application that displays large images, a proxy could delay loading an image until it is actually needed, saving memory and improving performance. Other common uses include controlling access to sensitive resources, caching results, and handling remote objects. This pattern is useful when you want to add an extra layer of control, security, or efficiency without modifying the original object's implementation. [Example with caching YouTube videos](https://refactoring.guru/design-patterns/proxy/java/example)

## Behavioral patterns
The **Chain of Responsibility Design Pattern** is a behavioral design pattern that allows a request to be passed along a chain of handlers, where each handler gets the opportunity to process the request or pass it to the next handler in the chain. Instead of having one object handle all possible requests using complex conditional statements, the responsibility is distributed among multiple objects, each responsible for a specific type of request. For example, in an employee approval system, a vacation request could first go to a team leader, then a manager, and finally a director, depending on the number of days requested. Each person either approves the request or forwards it to the next person in the chain. This pattern is useful when multiple objects could handle a request, as it reduces coupling between the sender and receiver and makes it easier to add or modify handlers without changing the existing client code. [Example with chain of handlers that perform various things such as authentication, authorization, and validation](https://refactoring.guru/design-patterns/chain-of-responsibility/java/example)

The **Iterator Design Pattern** is a behavioral design pattern that provides a way to access the elements of a collection sequentially without exposing its underlying structure or implementation. Instead of requiring the client to understand how a collection stores its elements, the iterator provides methods to navigate through the collection, such as checking whether another element exists and retrieving the next element. For example, when displaying a list of books in a library application, an iterator allows you to go through each book one by one without needing to know whether the books are stored in an array, linked list, or another data structure. This pattern is useful when you want to provide a consistent way to traverse different collections while keeping the collection's internal implementation hidden and separating traversal logic from the collection itself. [Example with spamming social media in lazy mode](https://refactoring.guru/design-patterns/iterator/java/example)

The **Memento Design Pattern** is a behavioral design pattern that allows an object's previous state to be saved and restored later without exposing its internal implementation details. It works by creating a memento object that stores a snapshot of the original object's state, which can then be used to restore the object to that exact state when needed. For example, in a text editor, the memento pattern can be used to implement an undo feature by saving snapshots of the document before each change, allowing users to revert to a previous version. This pattern is useful when you need to implement features such as undo and redo, save points, or state restoration while keeping the object's internal data encapsulated. [Example of backupping a collection of shapes by using their serializiblity](https://refactoring.guru/design-patterns/memento/java/example) 

The **State Design Pattern** is a behavioral design pattern that allows an object to change its behavior depending on its internal state, making it appear as though the object changes its class. Instead of using large conditional statements to handle different states, the pattern delegates the behavior to separate state classes, each representing a specific state of the object. For example, in a media player, the available actions depend on whether it is playing, paused, or stopped: pressing the play button might start playback when stopped but resume playback when paused. Each state handles the appropriate behavior and can transition the object into another state. This pattern is useful when an object's behavior changes depending on its state, as it reduces complex conditional logic, improves organization, and makes it easier to add new states without modifying existing code extensively. [Example of a music player with three states and four interface methods that can trigger state transitions](https://refactoring.guru/design-patterns/state/java/example)

The **Template Method Design Pattern** is a behavioral design pattern that defines the skeleton of an algorithm in a base class while allowing subclasses to override specific steps without changing the overall structure of the algorithm. Instead of implementing the entire algorithm separately in each subclass, the base class defines the sequence of steps, while subclasses provide their own implementations for certain steps. For example, in a coffee and tea preparation system, both drinks follow similar steps: boil water, prepare the drink, pour it into a cup, and add optional extras. The base class defines this common process, while subclasses implement the specific preparation steps for coffee or tea. This pattern is useful when multiple classes share a common workflow but need to implement certain steps differently, as it reduces code duplication, promotes code reuse, and ensures a consistent algorithm structure. [Example with Twitter and Facebook in which a general algorithm is given in the base social class and specialized in the subclasses](https://refactoring.guru/design-patterns/template-method/java/example)

The **Command Design Pattern** is a behavioral design pattern that turns a request or action into a standalone object, allowing it to be stored, passed around, executed, or undone independently of the object that performs the action. Instead of directly calling a method on an object, the client creates a command object that contains all the information needed to execute a specific action. For example, in a remote control system, each button could represent a command, such as turning on a TV, increasing the volume, or changing the channel. The remote control does not need to know how these actions are performed; it simply executes the corresponding command. This pattern is useful when you want to decouple the object requesting an action from the object performing it, and it makes features such as undo/redo functionality, action queuing, and logging easier to implement. [Example of an editor in which the commands copy/paste/select all/undo are stored as objects](https://refactoring.guru/design-patterns/command/java/example)

The **Mediator Design Pattern** is a behavioral design pattern that reduces direct communication between multiple objects by introducing a central mediator object that manages how they interact with each other. Instead of objects communicating directly and becoming tightly coupled, they send messages or notifications to the mediator, which coordinates the communication and determines which objects should respond. For example, in a group chat application, users do not send messages directly to every other user; instead, they send messages to a central chat room (the mediator), which distributes the messages to the other participants. This pattern is useful when multiple objects need to communicate with each other, as it reduces dependencies between them, centralizes communication logic, and makes the system easier to maintain and extend. [Example of a notes app in which many components interact inderectly via a concrete mediator](https://refactoring.guru/design-patterns/mediator/java/example)

The **Observer Design Pattern** is a behavioral design pattern that establishes a one-to-many relationship between objects, where multiple observer objects automatically get notified whenever a subject object changes its state. Instead of requiring observers to constantly check for changes, they subscribe to the subject and receive updates whenever an event occurs. For example, in a weather application, multiple devices or displays can subscribe to a weather station, and whenever the temperature changes, the weather station automatically notifies all its subscribers so they can update their displays. This pattern is useful when multiple objects need to stay synchronized with changes in another object, as it reduces coupling between objects and makes it easier to add or remove observers without modifying the subject's implementation. [Example of an editor which notifies email listener and log listener whenever there are changes](https://refactoring.guru/design-patterns/observer/java/example)

The **Strategy Design Pattern** is a behavioral design pattern that allows you to define a family of algorithms, encapsulate each one in a separate class, and make them interchangeable at runtime. Instead of implementing multiple algorithms using conditional statements within a single class, the pattern delegates the actual behavior to separate strategy classes that share a common interface. For example, in a navigation application, you could have different route-planning strategies, such as the fastest route, shortest route, or route that avoids toll roads. The user can switch between these strategies without changing the navigation system itself. This pattern is useful when you have multiple ways of performing an operation, as it reduces complex conditional logic, promotes code reuse, and makes it easier to introduce new algorithms without modifying existing code. [Example in which Paypal or Credit card can be used to pay](https://refactoring.guru/design-patterns/strategy/java/example)

The **Visitor Design Pattern** is a behavioral design pattern that allows you to add new operations to a group of existing classes without modifying their internal implementations. It works by creating a separate visitor object that contains the operations to be performed on different types of elements, while each element provides an accept() method that allows the visitor to perform the appropriate operation. For example, in a shopping cart application, you could have different product types, such as books, electronics, and clothing, and use a visitor to calculate taxes differently for each product without changing the product classes themselves. This pattern is useful when you need to perform multiple operations on a stable collection of different object types, as it separates operations from the objects they operate on and makes it easier to introduce new operations without modifying existing classes. [Example in which shapes are exported to XML by adding new behaviors to their existing class hierarchy](https://refactoring.guru/design-patterns/visitor/java/example)

## Concurrency patterns
The Active Object pattern Separates method invocation from method execution by processing requests asynchronously in a dedicated thread. Requests are placed in a queue and executed independently of the calling thread, allowing clients to continue without waiting for operations to finish.

The **Monitor Object pattern** Encapsulates shared data and synchronization within an object, ensuring that only one thread at a time can execute protected methods or access critical sections. This prevents race conditions and maintains data consistency.

The **Half-Sync/Half-Async pattern** Separates asynchronous event handling from synchronous task processing. An asynchronous layer handles incoming events, while a synchronous layer processes tasks, typically communicating through a queue. This simplifies concurrency management and separates different processing responsibilities.

The **Leader/Followers pattern** Coordinates multiple threads that handle incoming events. One thread acts as the leader and waits for the next event, while the remaining threads act as followers. Once the leader receives an event, it processes or delegates it and another follower becomes the new leader.

The **Producer-Consumer pattern** Separates data production from data consumption using a shared thread-safe queue. Producers generate and enqueue data, while consumers retrieve and process it independently. This decouples processing speeds and enables asynchronous communication between threads.

The **Thread Pool pattern** Maintains a collection of reusable worker threads that execute submitted tasks. Instead of creating a new thread for every task, tasks are assigned to available workers, reducing thread creation
